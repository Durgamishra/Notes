Introduction

Data Acquisition & Sanitization in Data Science

📈 The Modern Data Wrangling Lifecycle

In modern data science, raw data gathered from the real world is almost never immediately usable. Data acquisition (obtaining data) and data preprocessing (cleaning and wrangling) represent the foundational phase of any analytical pipeline. Empirical studies show that data scientists spend approximately 60% to 80% of their operational project time discovering, extracting, auditing, cleaning, and transforming raw inputs before building statistical models or deploying machine learning algorithms.

Raw data is harvested from disparate and heterogeneous systems—such as web scraped pages, REST APIs, enterprise relational databases (SQL), document stores (NoSQL), IoT hardware sensor logs, and proprietary file formats (Excel, CSV, SPSS). Because these data generators operate independently under varying standards, the extracted datasets inherently suffer from systemic structural and statistical imperfections. These include missing values, duplicate records, non-standard text encodings, date formatting conflicts, trailing whitespace, and extreme statistical outliers.

Data cleaning systematically identifies, diagnoses, and corrects these errors. High-quality data is the fundamental prerequisite for valid statistical inference, robust analytical charts, and actionable executive decisions. The classic computing axiom "Garbage In, Garbage Out" (GIGO) summarizes this dependency: even the most sophisticated deep learning architecture or predictive regression model will yield inaccurate, biased, and misleading outputs if trained on dirty or uncalibrated data.

📌 Core Exam Takeaways: Data Quality Dimensions

  • Accuracy: Degree to which recorded values conform to real-world true values.
  • Completeness: Absence of missing records, null fields, or omitted observations.
  • Consistency: Uniform formatting and structure across integrated datasets (e.g., standardizing "M"/"Male").
  • Timeliness: How recently the data was gathered to reflect current conditions.
  • Uniqueness: Elimination of redundant or duplicated data rows.
Topic 1

Obtaining Data from the Web

🌐 Web Data Extraction & Web Scraping Mechanics

The World Wide Web serves as an expansive, unstructured data repository containing millions of public web pages, commercial catalogs, financial portals, and news archives. Obtaining data from the web involves extracting structured tabular data or unorganized text directly from HTML web documents. While some platforms provide downloadable CSV or JSON files, much of the web's valuable information is embedded in raw HTML markup, requiring automated programmatic extraction known as Web Scraping or Web Crawling.

Web scraping relies on understanding the Document Object Model (DOM)—the hierarchical tree structure created by web browsers when parsing HTML markup. Scraping tools submit HTTP GET requests to target URLs, fetch raw HTML text, parse the DOM tree, and isolate specific content using CSS Selectors (e.g., .class-name, #id-name) or XPath Expressions (e.g., //table[@class='data-table']). In the R language, web scraping is primarily driven by the rvest and httr packages.

📂 Primary Web Data Sources

1. Public Repositories

Curated, structured open data portals (e.g., Kaggle, Data.gov, World Bank Open Data) providing ready-to-use downloadable datasets in CSV or Parquet format.

2. HTML Web Scraping

Automated DOM parsing of unstructured web pages (e.g., e-commerce price catalogs, Wikipedia tables, stock market ticker pages) into structured data frames.

3. Social Media & Forums

Extracting public posts, comments, and engagement counters across forums for sentiment analysis and natural language processing (NLP).

⚠ Ethical Rules & Web Scraping Guidelines

  • Robots.txt Protocol: Always inspect a site's robots.txt file (e.g., domain.com/robots.txt) to check disallowed paths and crawler crawling rules.
  • Rate Limiting: Introduce time delays between requests (e.g., Sys.sleep(2)) to prevent overloading target web servers (Denial of Service).
  • User-Agent Identification: Supply clear contact headers in scraping requests so site administrators can identify your script.
R Script - Downloading Web Files & Scraping HTML Tables with rvest 
library(rvest)
library(httr)

# 1. Download a Remote File Directly
file_url <- "https://raw.githubusercontent.com/datasets/gdp/master/data/gdp.csv"
download.file(url = file_url, destfile = "gdp_data.csv", method = "curl")
gdp_data <- read.csv("gdp_data.csv")

# 2. Scraping HTML Tables from Wikipedia using rvest
target_url <- "https://en.wikipedia.org/wiki/List_of_countries_by_GDP_(nominal)"

# Fetch HTML content with custom User-Agent header
webpage <- GET(target_url, add_headers(`User-Agent` = "BCA_DataScience_Student_Bot/1.0")) %>%
  read_html()

# Extract table elements using CSS selectors
table_nodes <- html_nodes(webpage, css = "table.wikitable")

# Convert the first HTML table into an R Data Frame
gdp_table <- html_table(table_nodes[[1]], fill = TRUE)
head(gdp_table)

Obtaining Data from APIs

📌 REST API Architecture & Protocol Mechanics

An Application Programming Interface (API) is a formal software intermediary that enables distinct computer programs to exchange data programmatically over standard internet protocols. In modern data science pipelines, RESTful (Representational State Transfer) APIs serve as the preferred method for automated data collection. Unlike web scraping—which fragilely parses unstructured HTML presentational code—APIs deliver pure, highly structured data directly from server backend databases, bypassing visual layout elements entirely.

REST APIs communicate over standard HTTP/HTTPS channels using defined verbs:

  • GET: Requests and retrieves data records from the server (primary verb used in data ingestion).
  • POST: Submits new data or query payloads to the server.
  • PUT / PATCH: Updates existing server data records.
  • DELETE: Removes a resource from the target database.

API responses return structured payloads serialized in either JSON (JavaScript Object Notation) or XML (eXtensible Markup Language). JSON is the dominant web standard due to its lightweight key-value pair and array format, which maps directly into programming data structures like lists and data frames.

🐦 Step-by-Step API Ingestion Workflow

  1. Registration & Credentials: Register on the API provider portal to acquire an API Key or OAuth 2.0 Client Credentials for authentication and rate-limit tracking.
  2. Request Formulation: Construct the request URL endpoint, appending query parameters (e.g., ?city=Bhubaneswar&units=metric) and passing security keys in HTTP headers.
  3. HTTP Dispatch: Issue the HTTP request via client libraries (such as httr in R or requests in Python).
  4. Status Code Inspection: Verify the HTTP status code returned by the server:
    • 200 OK: Request succeeded; payload delivered.
    • 401 Unauthorized: Missing or invalid API key credentials.
    • 404 Not Found: Target endpoint or resource does not exist.
    • 429 Too Many Requests: Rate limit exceeded.
    • 500 Internal Server Error: Remote server application crashed.
  5. Payload Deserialization: Parse the raw JSON text response into a structured data frame using packages like jsonlite.
R Script - Querying REST API and Deserializing JSON Data 
library(httr)
library(jsonlite)

# Define API URL Endpoint and Request Parameters
base_url <- "https://api.openweathermap.org/data/2.5/weather"
query_params <- list(
  q = "Bhubaneswar",
  appid = "YOUR_API_KEY_HERE",
  units = "metric"
)

# Dispatch HTTP GET Request
response <- GET(url = base_url, query = query_params)

# Check HTTP Response Status Code
if (status_code(response) == 200) {
  # Parse raw text body into JSON object
  json_content <- content(response, as = "text", encoding = "UTF-8")
  
  # Flatten JSON tree directly into a usable R list/data frame
  weather_df <- fromJSON(json_content, flatten = TRUE)
  
  cat("City:", weather_df$name, "\nTemp:", weather_df$main$temp, "°C\n")
} else {
  cat("API Request Failed with Status Code:", status_code(response), "\n")
}

Obtaining Data from Databases

💾 Enterprise Database Architectures

Enterprise application backends, transactional logs, and commercial software systems store operational data inside centralized database management systems. Connecting directly to enterprise databases allows data scientists to extract historical records, run aggregations, and pull filtered subsets without overloading local computer memory. Databases fall into two primary structural categories:

🗄 Relational (RDBMS) vs. NoSQL Databases

1. Relational Databases (RDBMS): Organize data into strictly defined 2D tables consisting of columns (attributes) and rows (tuples). Relationships across tables are defined using Primary and Foreign keys. Querying is executed using Structured Query Language (SQL), which allows data filtering, joining, and aggregation directly on the remote database server before pulling results into local memory. Common RDBMS engines include PostgreSQL, MySQL, Oracle, SQLite, and Microsoft SQL Server.

2. NoSQL (Not Only SQL) Databases: Built to store unstructured, semi-structured, or high-velocity data that does not fit into fixed schema tables. Schema flexibility allows developers to ingest diverse data formats without upfront schema definition. NoSQL types include:

  • Document Stores: Store hierarchical BSON/JSON documents (e.g., MongoDB).
  • Key-Value Stores: In-memory key-indexed lookup systems (e.g., Redis).
  • Column-Family Stores: Distributed wide-column engines (e.g., Apache Cassandra).
  • Graph Databases: Network node-and-edge engines (e.g., Neo4j).

📌 The Database Connection Lifecycle in R

  1. Load Driver: Load DBI database interfaces (e.g., library(DBI), library(RSQLite)).
  2. Connect: Open connection handle via dbConnect(RSQLite::SQLite(), dbname="db.sqlite").
  3. Execute SQL: Submit SQL string using dbGetQuery(conn, "SELECT ... WHERE ...").
  4. Fetch: Extract the query output directly into an R data frame.
  5. Close Handle: Always terminate the channel using dbDisconnect(conn) to prevent connection pool leaks.
R Script - Executing SQL Queries on SQLite Database using DBI 
library(DBI)
library(RSQLite)

# 1. Establish Driver Connection to Local SQLite Database
conn <- dbConnect(RSQLite::SQLite(), dbname = "company_warehouse.sqlite")

# 2. Write Parameterized SQL Query
sql_query <- "
  SELECT Department, COUNT(EmployeeID) AS StaffCount, AVG(Salary) AS AvgSalary
  FROM Employees
  WHERE JoinYear >= 2021
  GROUP BY Department
  HAVING AVG(Salary) > 45000
"

# 3. Execute SQL statement and retrieve data frame directly
result_df <- dbGetQuery(conn, sql_query)
print(result_df)

# 4. Explicitly Disconnect Handle
dbDisconnect(conn)

Topic 5

Data Cleaning Overview

🧹 Principles of Data Sanitization

Data Cleaning (also known as data cleansing, scrubbing, or data wrangling) is the structured process of auditing raw datasets to detect, diagnose, and remediate corrupted, inaccurate, incomplete, duplicated, incorrectly formatted, or statistically anomalous records. Raw data collected from operational web forms or manual entries is notoriously noisy.

A comprehensive data auditing workflow follows a structured lifecycle:

  1. Data Auditing & Profiling: Inspecting summary statistics, data types, missing value percentages, and value distributions using functions like summary(), str(), and glimpse().
  2. Defining Sanitization Rules: Establishing validation logic (e.g., Age must be between 0 and 120; Email must contain "@").
  3. Execution of Cleaning Actions: Running transformations to handle missing data, drop duplicate records, fix formatting errors, and treat outliers.
  4. Post-Verification: Re-auditing clean datasets to confirm that structural integrity is preserved without introducing accidental processing bias.
Topic 6

Handling Missing Data

❌ Statistical Missingness Mechanisms

Missing data occurs when no data value is stored for an observation attribute. In R, missing values are denoted by the logical constant NA (Not Available), whereas uncomputable mathematical operations yield NaN (Not a Number). Missingness can occur due to respondent non-response in surveys, equipment hardware faults, or data extraction drops. To choose the correct remediation method, data scientists evaluate three primary missingness mechanisms:

  • 1. Missing Completely at Random (MCAR): The probability of data being missing is completely independent of both observed variables and unobserved parameters. Missingness is purely accidental (e.g., a laboratory sample accidentally dropped on the floor).
  • 2. Missing at Random (MAR): Missingness depends systematically on observed dataset variables, but not on the missing value itself (e.g., male survey participants being statistically less likely to fill out depression questionnaire fields).
  • 3. Missing Not at Random (MNAR): Missingness depends directly on the unobserved missing value itself (e.g., high-income earners deliberately skipping income fields on tax surveys).

🛠 Remediation Strategies & Imputation Techniques

Listwise Deletion

Purging entire observation rows containing any NA using na.omit() or complete.cases(). Simple, but discards statistical power and introduces bias if data is not MCAR.

Mean/Median Imputation

Replacing missing numerical entries with column Mean (symmetric distributions) or Median (skewed distributions). Preserves sample size but artificially shrinks feature variance.

Mode Imputation

Replacing missing categorical text values with the most frequently occurring categorical class value in the column.

Advanced Predictive Imputation

Estimating missing values using k-Nearest Neighbors (k-NN) or Multiple Imputation by Chained Equations (MICE) based on surrounding correlated features.

R Script - Detecting & Imputing Missing Values in R 
# Sample Data Frame with Missing Values
df <- data.frame(
  ID = 1:5,
  Salary = c(50000, 60000, NA, 75000, 52000),
  Age = c(25, NA, 30, 45, 22)
)

# 1. Identify missing entries globally
is.na(df)
sum(is.na(df$Salary)) # Count NAs in Salary column

# 2. Strategy A: Complete Case Analysis (Listwise Deletion)
clean_complete <- na.omit(df)

# 3. Strategy B: Median Imputation for Numerical Salary
median_salary <- median(df$Salary, na.rm = TRUE)
df$Salary[is.na(df$Salary)] <- median_salary

print(df)
Topic 7

Removing Duplicate Data

🔁 Duplicate Mechanics & Analytical Risks

Duplicate data refers to identical or highly redundant records present within a dataset. Duplication typically occurs during bulk data extraction from multiple operational servers, repeated submission of online forms, or outer join operations performed across relational database tables.

Failing to identify and purge duplicate records introduces severe errors into analytical pipelines:

  • Artificially Inflated Sample Sizes: Overcounts underlying metrics (e.g., doubling total sales revenues or active user counts).
  • Distorted Summary Statistics: Distorts statistical calculations including mean, standard deviation, and variance estimates.
  • Model Overfitting: Machine learning algorithms trained on duplicated rows give improper weight to repeated records, compromising generalization performance on unseen test data.
R Script - Detecting & Removing Duplicates using Base R and dplyr 
library(dplyr)

# Sample Data Frame containing Duplicate Rows
df_dup <- data.frame(
  CustomerID = c(101, 102, 102, 103, 101),
  Name = c("Alice", "Bob", "Bob", "Charlie", "Alice"),
  Score = c(85, 90, 90, 95, 85)
)

# 1. Identify duplicate rows (returns logical vector)
duplicated(df_dup)

# 2. Strategy A: Deduplicate using Base R unique()
df_unique_base <- unique(df_dup)

# 3. Strategy B: Deduplicate using dplyr distinct()
df_unique_dplyr <- df_dup %>% distinct()

# 4. Deduplicate based on specific key column (e.g., CustomerID)
df_unique_key <- df_dup %>% distinct(CustomerID, .keep_all = TRUE)
print(df_unique_key)
Topic 8

Data Formatting & Standardisation

📝 String Parsing, Date Conversions & Type Coercion

Inconsistent data formatting occurs when attributes meant to store uniform values are recorded using varying expressions, character encodings, text cases, or units of measurement. In multi-source integration projects, a single categorical attribute like gender might be recorded as "Male", "male", "M", "m " (with whitespace), or 1. Standardisation enforces strict structural uniform patterns across all features.

Core standardisation operations include:

  • Trimming Whitespace: Stripping hidden leading, trailing, and repeated interior spaces using stringr::str_trim() or trimws().
  • Text Case Normalization: Converting all text fields to lowercase or uppercase using tolower() or toupper() to enable clean grouping aggregations.
  • Character String Stripping: Removing non-numeric symbols (e.g., stripping "$", "%", or "," from currency text fields) and casting strings into numeric primitives using as.numeric().
  • ISO Date Standardisation: Parsing inconsistent string dates (e.g., mixing "12/05/2026", "2026-May-12", "12-05-26") into unified ISO 8601 Date objects (YYYY-MM-DD) using the lubridate library.
R Script - String Cleaning and Date Formatting with stringr & lubridate 
library(stringr)
library(lubridate)

# Messy Input Data Frame
messy_df <- data.frame(
  Price_Text = c(" $1,200.50 ", "$450.00", " $89.99 "),
  Gender_Raw = c(" Male", "female", "MALE "),
  Raw_Date = c("2026-10-04", "04/10/2026", "October 4, 2026")
)

# 1. Clean String Prices -> Convert to Clean Numeric Primitives
messy_df$Clean_Price <- messy_df$Price_Text %>%
  str_trim() %>%                   # Strip whitespace
  str_remove_all("[$,]") %>%       # Remove currency symbols & commas
  as.numeric()                     # Cast to numeric primitive

# 2. Standardize Categorical Text Casing
messy_df$Clean_Gender <- messy_df$Gender_Raw %>%
  str_trim() %>%
  tolower()

# 3. Parse Inconsistent Strings into Standard ISO Dates using lubridate
messy_df$Clean_Date <- parse_date_time(messy_df$Raw_Date, orders = c("ymd", "dmy", "B d, Y"))

print(messy_df)
Topic 9

Handling Outliers

📈 Statistical Detection Rules & Remediation

An Outlier is an extreme statistical observation that deviates significantly from the central tendency of a feature distribution. Outliers stem from data entry errors (e.g., recording a patient's age as 250), instrument sensor miscalibrations, or genuine natural variation (e.g., extreme wealth distribution in economic datasets). Unmanaged outliers heavily distort mean calculations, inflate sample variances, and alter Ordinary Least Squares (OLS) regression coefficients.

📏 Parametric vs. Non-Parametric Detection Methods

1. Interquartile Range Method (IQR - Non-Parametric): Ideal for skewed data distributions. Calculates the distance between the 25th percentile ($Q_1$) and the 75th percentile ($Q_3$).

IQR = Q3 - Q1
Lower Bound = Q1 - 1.5 * IQR  |  Upper Bound = Q3 + 1.5 * IQR

Any observation falling below the Lower Bound or above the Upper Bound is flagged as a statistical outlier.

2. Z-Score Method (Parametric): Ideal for normally distributed bell-curve features. Measures how many standard deviations ($\sigma$) an individual observation ($x$) lies away from the population mean ($\mu$).

Z = (x - μ) / σ

Observations with an absolute Z-score $|Z| > 3.0$ are flagged as extreme statistical outliers.

🛠 Outlier Treatment Strategies

  • Trimming / Truncation: Dropping outlier rows entirely from the dataset.
  • Winsorization (Capping): Setting values beyond the upper boundary equal to the 99th percentile ($P_{99}$) value, and values below the lower boundary to the 1st percentile ($P_1$) value.
  • Mathematical Log Transformation: Applying a natural logarithm ($\ln(x)$) to compress long-tailed right-skewed distributions.
R Script - IQR & Z-Score Outlier Detection and Capping 
# Vector containing an extreme statistical outlier (500)
age_vector <- c(22, 25, 24, 23, 26, 28, 22, 21, 500)

# 1. Non-Parametric IQR Outlier Detection
Q1 <- quantile(age_vector, 0.25)
Q3 <- quantile(age_vector, 0.75)
IQR_val <- Q3 - Q1

lower_bound <- Q1 - (1.5 * IQR_val)
upper_bound <- Q3 + (1.5 * IQR_val)

outliers <- age_vector[age_vector < lower_bound | age_vector > upper_bound]
cat("Detected Outliers via IQR:", outliers, "\n")

# 2. Winsorization (Capping Outliers to Upper Bound)
clean_age <- age_vector
clean_age[clean_age > upper_bound] <- upper_bound
print(clean_age)

Data Transformation & Feature Scaling

⚙ Normalization vs. Standardization Formulas

Feature scaling converts numerical attributes measured across vastly different scales into a uniform range. For instance, combining an Age feature (ranging from 18 to 80) with a Salary feature (ranging from $20,000 to $500,000) inside distance-based algorithms (like k-NN, k-Means, or SVM) causes the high-magnitude Salary feature to completely dominate distance calculations. Feature scaling normalizes these relative magnitudes.

1. Min-Max Normalization

Rescales all numeric feature values into a fixed range between 0.0 and 1.0. Bounded min-max normalization is ideal when the algorithm requires bounded numerical inputs (e.g., neural networks), but remains sensitive to extreme outliers.

X' = (X - X_min) / (X_max - X_min)

2. Z-Score Standardization

Rescales data to have a statistical Mean ($\mu$) equal to 0.0 and a Standard Deviation ($\sigma$) equal to 1.0. Standardization handles statistical outliers better than min-max scaling and does not bound data into a rigid interval.

Z = (X - μ) / σ

3. Logarithmic Transformation

Applies $\log_e(X)$ or $\log_{10}(X)$ to linearize exponential relationships and stabilize variance across right-skewed positive features (e.g., income metrics, population counts).

R Script - Executing Min-Max Scaling and Z-Score Standardization 
salary_vals <- c(30000, 45000, 50000, 80000, 120000)

# 1. Custom Min-Max Normalization Function [0, 1]
min_max_scale <- function(x) {
  return((x - min(x)) / (max(x) - min(x)))
}
scaled_minmax <- min_max_scale(salary_vals)

# 2. Z-Score Standardization using Base R scale() function
scaled_zscore <- scale(salary_vals) # Mean = 0, Std Dev = 1

# 3. Log Transformation
scaled_log <- log(salary_vals)

df_scaled <- data.frame(Raw = salary_vals, MinMax = scaled_minmax, ZScore = as.vector(scaled_zscore), Log = scaled_log)
print(df_scaled)

Making Data "Tidy"

🔄 Hadley Wickham's Tidy Data Principles

Formulated by statistician Hadley Wickham, Tidy Data provides a standardized structural framework linking the physical layout of a 2D data frame directly with its underlying statistical meaning. Structuring datasets in tidy format simplifies exploratory data analysis, plotting, and model fitting.

📜 The 3 Core Rules of Tidy Data (Exam Mandatory)

  1. Rule 1: Each variable must form its own unique column.
  2. Rule 2: Each observation (case) must form its own unique row.
  3. Rule 3: Each value must occupy its own individual cell.

🛠 Reshaping Verbs in tidyr

Untidy datasets (often termed wide or messy data) frequently violate these rules—such as placing variable names (like year values "2024", "2025") as column headers. The tidyr package provides reshape functions to correct these issues:

  • pivot_longer(): Reshapes wide datasets into long formats by gathering column headers into a new variable column.
  • pivot_wider(): Reshapes long datasets into wide formats when multiple observation attributes are stacked in a single column.
  • separate(): Splits a single combined text column into multiple distinct variable columns based on a delimiter (e.g., splitting "City_State" into "City" and "State").
  • unite(): Combines values from multiple columns into a single unified column.
R Script - Reshaping Messy Data into Tidy Data using tidyr 
library(tidyr)
library(dplyr)

# Untidy Wide Data Frame (Year variables stored in column headers)
untidy_df <- data.frame(
  Country = c("India", "USA"),
  Year_2024 = c(1000, 2000),
  Year_2025 = c(1100, 2100)
)
print(untidy_df)

# Reshape into Tidy Format using pivot_longer()
tidy_df <- untidy_df %>%
  pivot_longer(
    cols = starts_with("Year_"),
    names_to = "Year",
    names_prefix = "Year_",
    values_to = "GDP_Value"
  )

print(tidy_df)
# Output complies fully with Tidy Data Rules: Country | Year | GDP_Value

Web Scraping

Parses HTML DOM elements using CSS selectors (rvest). Always follow robots.txt.

REST APIs

Exchanges structured JSON/XML payloads using HTTP verbs (GET) and authentication tokens.

Missing Data

Represented by NA in R. Remediated via Listwise Deletion or Mean/Median Imputation.

IQR Outlier Rule

Bounds: Q1 - 1.5*IQR to Q3 + 1.5*IQR. Outliers treated via capping or trimming.

Feature Scaling

Min-Max scales to [0,1]. Z-Score normalizes to Mean=0 and StdDev=1.

Tidy Data

Variables = Columns | Observations = Rows | Values = Cells. Reshaped via pivot_longer().
